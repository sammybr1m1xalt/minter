APPENDED 2026-11-06 — SITE SCANNER → eth_call → GENERIC MINT PIPELINE
================================================================================

The idea: point the minter at ANY website, discover the contract address from
the page/JS, verify it on-chain with eth_call, identify the platform, and mint —
using a specific adapter when one exists and the generic probe when it doesn't.

This is the right shape. It is also the highest-risk thing in this file, because
the last step is a state-changing transaction built from data scraped off a
webpage. The design below is built around making that step safe.

--------------------------------------------------------------------------------
S1. CA extractor — generalise beyond OpenSea
--------------------------------------------------------------------------------
Today: slug-resolver.ts:13 htmlScrapeCollection() is one regex against one URL.
It matches the FIRST "address":"0x…" in the page. Verified: an OpenSea collection
page contains 154 unique 40-hex strings (WETH, USDC, staked tokens, other
collections). The first one happened to be right for `collectr`. That is luck,
not design.

Build:
  - extractAddresses(html): string[] — every 0x + 40 hex, deduped, in document
    order, each tagged with the JSON key it appeared under and a byte offset.
  - extractFromScripts(html): also parse <script> bodies and any
    self.__next_f.push(...) / JSON blobs — many sites embed config there.
  - Per-site adapters that know which field is authoritative:
      OpenSea  → "address" in the collection payload
      Manifold → contractAddress in the claim payload
      Zora     → addresses[] in the collection config
      generic  → ranked heuristic (see S2)
  - Return candidates with a confidence + source, not a single address.

--------------------------------------------------------------------------------
S2. Candidate ranking (when there is no site-specific adapter)
--------------------------------------------------------------------------------
Rank every extracted address by evidence, highest first:
  1. appears under a key named address / contract / contractAddress / nftContract
  2. appears in a "contracts":[...] block
  3. appears more than once on the page
  4. appears in a <script> JSON blob rather than visible text
  5. is referenced by an on-page "mint" button's href/data attribute
Deduct for: the zero address, WETH/USDC/DC known token addresses, addresses that
appear only in a footer or "powered by" block.

--------------------------------------------------------------------------------
S3. On-chain verification — eth_getCode, then interface probes
--------------------------------------------------------------------------------
This is the step that makes the rest safe, and it does not exist yet.
`grep eth_getCode src/*.ts` → nothing.

For each candidate, in parallel:
  1. eth_getCode(address) — empty means EOA or non-contract. Drop it.
     This single call kills the "scraped a token address" failure mode.
  2. ERC165 supportsInterface for ERC721 (0x80ac58cd), ERC1155 (0xd9b67a26),
     ERC721Enumerable (0x780e9d63), ERC1155MetadataURI (0x0e89341c).
  3. Fallback probes when ERC165 is absent (many older contracts):
     balanceOf(address), balanceOf(address,uint256), ownerOf(uint256).
  4. Known-singleton check: is the address the SeaDrop v1/v2 singleton, a
     known Manifold contract, a known Zora minter? (see S4)

Output: { address, chainId, isContract, standard, platform, confidence }.
Only candidates that pass isContract continue.

CHAIN AWARENESS: the scanner must try the chain the page indicates, then fall
back through the chains in CHAINS[]. An address that is a contract on Base and
an EOA on Ethereum is a Base contract. Do not assume Ethereum.

--------------------------------------------------------------------------------
S4. Platform registry — specific adapters before generic
--------------------------------------------------------------------------------
Order matters. A specific adapter is always preferred over the generic probe.

  1. SeaDrop singleton (v2 0x00005EA0…, v1 0x00000000…06c3852c…)
       → seadrop-onchain.ts (already built, already chain-aware)
       → require POSITIVE EVIDENCE (configured drop / non-zero merkle root /
         registered fee recipient), not a non-reverting call
  2. OpenSea-managed drop
       → fcfs-drops.ts / fcfs-mint.ts (already built)
  3. Manifold
       → mint-plan.ts resolveManifoldClaim (R6, to be rebuilt)
  4. Zora
       → mint(address,uint256,address,uint256,bytes) — needs its own encoder
  5. scatter.art
       → scatter.ts (R3, to be rebuilt)
  6. GENERIC PROBE (R1 mint-generic.ts) — last resort only

Each adapter declares: how to detect it, how to read mint parameters, how to
encode the call, and what off-chain data it needs. If detection is not positive,
do not use the adapter.

--------------------------------------------------------------------------------
S5. The generic mint step — where the risk lives
--------------------------------------------------------------------------------
This is the part that must never be allowed to guess.

HARD RULES:
  - Never mint against a contract you have not positively identified (S3+S4).
  - Never encode a parameter you cannot derive. If a mint needs a merkle proof
    or an EIP-712 signature and none is configured, SKIP that selector and say
    why. Guessing a bytes32[] or a signature is how you burn gas on a revert or
    worse.
  - Simulate before signing: provider.call() the exact transaction. A revert is
    a hard stop, not a warning. (The JS original does this in mintOne; the TS
    port currently does NOT — see the minting-logic section above.)
  - Check balance >= mintValue + gasLimit × maxFeePerGas before broadcasting.
  - Respect a price cap (price-protection.ts, R2) — refuse if the detected price
    exceeds it.

--------------------------------------------------------------------------------
S6. What "scan any site's JS" can and cannot do
--------------------------------------------------------------------------------
Be honest about this in the UI and in the code comments.

A modern mint site is a React/Next app. The contract address is usually NOT in
the HTML you get from a plain fetch — it is fetched from the project's own API
after hydration, or injected at build time into a JSON payload.

What works with a plain fetch:
  - addresses embedded in the initial HTML/JSON payload
  - addresses in <script> blobs
  - addresses in server-rendered markup

What does NOT work without a headless browser:
  - addresses loaded by a client-side API call after page load
  - addresses rendered behind a "connect wallet" interaction
  - Cloudflare-challenged pages (you get the challenge, not the page)

Do NOT add Puppeteer/Playwright by default. It is a ~300MB Chromium dependency
and a much slower, more fragile path. Make it an opt-in adapter for sites that
are otherwise unreachable, and say clearly in the output when a site returned
nothing.

--------------------------------------------------------------------------------
S7. Suggested module layout
--------------------------------------------------------------------------------
  src/site-scanner.ts     — extractAddresses, extractFromScripts, ranking (S1, S2)
  src/contract-verify.ts  — eth_getCode, ERC165, fallback probes (S3)  [NEW FILE]
  src/platform-registry.ts— detection + dispatch order (S4)             [NEW FILE]
  src/mint-generic.ts     — the generic encoder (R1, already in the to-do)
  src/price-protection.ts — the guard (R2, already in the to-do)

contract-verify.ts is the highest-value new file: it is the gate that makes
everything downstream trustworthy, and it is small.

--------------------------------------------------------------------------------
S8. Tests
--------------------------------------------------------------------------------
  - extractAddresses on a saved HTML fixture: assert it finds N addresses and
    ranks the collection address first.
  - A page with NO addresses returns [] — not a wrong address.
  - eth_getCode against a known EOA returns empty → candidate dropped.
  - eth_getCode against a known contract returns non-empty → candidate kept.
  - ERC165 probe against a live ERC721 and a live ERC1155 → correct standard.
  - A scraped address that is a token (WETH) must be rejected by ranking.
  - Generic mint: a contract with no recognized mint function returns
    "not recognized", never a guessed selector.
  - Generic mint: a selector requiring a proof is SKIPPED when no proof source
    is configured.
  - Simulation gate: a reverting call must stop the flow, not broadcast.

--------------------------------------------------------------------------------
S9. Order of work
--------------------------------------------------------------------------------
  1. contract-verify.ts (S3)        — the safety gate; small, testable, live
  2. site-scanner.ts (S1, S2)       — extraction + ranking
  3. platform-registry.ts (S4)      — dispatch, wired to existing adapters
  4. generic mint (R1)              — already in the to-do; needs S5's rules
  5. headless-browser adapter (S6) — only if a real site needs it

Do 1 before 2. Verification before extraction is what makes extraction safe.
