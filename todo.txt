[DONE 2026-11-12] T1.5  opensea-gql.ts:756 + fcfs-drops.ts:909 — THE PER-WALLET CAP IS READ
       FROM THE WRONG FIELD. Docs-checked and reproduced.
       The code takes `maxPerWallet` from
       `stages[].eligibleMaxTotalMintableByWallet ?? maxTotalMintableByWallet`
       — that is the STAGE's own cap. The wallet's running cap lives in
       `accountStageEligibility.wallets[].stages[].maxTotalMintableByWallet`,
       which the code queries (opensea-gql.ts:46) and then NEVER READS: the
       block is used only to count other wallets' eligibility (763-778).
       What the docs say (REST `max_total_mintable_by_wallet`, same name and
       semantics on the GQL account block):
         "The wallet's running cap through this stage ... the limits of every
          stage up to and including this one that the wallet is listed on,
          added together, clamped to supply. The public stage's own limit is
          added only on the public stage's result, not on any presale's. ...
          subtract what the wallet has minted to get what it can still mint."
       Reproduced live on jpegz with a wallet that is NOT allowlisted:
         b88e9d05… SIGNED_PRESALE eligible=false  cap=100  walletMintable=100
         619ce693… SIGNED_PRESALE eligible=false  cap=1    walletMintable=1
         f3de2b08… SIGNED_PRESALE eligible=false  cap=2    walletMintable=2
         af6f0359… PUBLIC_SALE    eligible=true   cap=2    walletMintable=2
       The raw GQL account block for the same wallet says
       maxTotalMintableByWallet = null, null, null, 2 — i.e. the presales have
       NO cap for this wallet. The report says it can mint 100/1/2. Wrong.
       Two parts to fix:
         (a) read the running cap from the account block, keyed by dropStageUuid
               and matched to the queried wallet;
         (b) when eligible === false, walletMintable must be 0 (or null), not
               the stage's own cap — mintableFromCap ignores an unknown
               runningCap and falls back to phaseLimit, which is how a
               non-eligible wallet ends up quoted a six-figure allowance.
       For an eligible wallet this also UNDERSTATES: the running cap is the sum
       of the wallet's listed stages up to this one, not this stage's own limit.

[DONE 2026-11-12] T3.13 GQL hash handling — external-audit recommendation, assessed 2026-11-11.
       Recommendation: "auto-discover the current hash from the OpenSea
       frontend in case OpenSea rotates it." VERDICT: do NOT scrape the
       frontend; the recommendation solves a problem that is already handled,
       and the real gap is smaller.
       Facts established by reading the code and computing the hashes:
         - Only ONE pinned hash is ever used: GQL_HASHES.mintTimeline, for
           MintActionTimelineQuery (opensea-gql.ts:571). The other four
           (mintModule, dropEligibility, mintQuery, collectionDrops) are
           dead — never referenced anywhere.
         - That pinned hash is exactly sha256 of OUR OWN query text
           (verified: 1a786dd183540c6143038435ebb7d48c6e2007150210585e45137c8e1d779801
           matches). It is not a frontend secret.
         - DropEligibilityQuery uses gqlApqQuery, which always computes the
           hash locally and POSTs — immune to rotation entirely.
       So a rotation can only mean OpenSea dropped our registered hash, and
       gqlPersistedQuery's APQ fallback re-registers and executes in the SAME
       call. Correctness is never at risk; the cost is one extra round trip
       on the first affected call.

       pinned hash first and pays the APQ penalty again. Remember the working
       hash in-module (optionally persist it to .minter-cache/) or skip the
       hash-only GET once an APQ registration has happened in this process.
       Also: delete the four dead hashes.

DOCS-CHECKED 2026-11-12 (docs.opensea.io, eligibility + auth pages)
-----------------------------------------------------------------
Authoritative contract for GET /api/v2/drops/{slug}/eligibility:
  - Auth: ApiKeyAuth + WalletAuth with scope `read:eligibility`.
    WalletAuth = `Authorization: Bearer <wallet JWT>` — NOT the SIWE cookie.
  - 200 -> { stages: [ { is_eligible (REQUIRED, boolean),
                         stage_uuid (REQUIRED, uuid),
                         max_total_mintable_by_wallet (string|null),
                         max_total_mintable_by_wallet_per_token (string|null),
                         price (string|null, WEI decimal) } ] }
  - So the REST surface gives a DEFINITIVE per-stage verdict and a wei price.

What that means for this codebase:
  1. The REST fallback is structurally unreachable. fetchRestEligibility sends
     a Bearer derived from the SIWE access_token (bearerFromSessionCookie);
     the docs are explicit that wallet-scoped REST needs a wallet JWT, and the
     SIWE session is only for managing PATs. The auth page gives the missing
     link: a scoped PAT can be exchanged for a wallet JWT at
     /api/v2/auth/tokens/exchange. Not implemented anywhere in src/.
     -> GQL stays the only working wallet-scoped surface. Recorded as T2.11.
  2. Price units are settled, not ambiguous: REST `price` = wei, GQL
     `eligiblePrice.token.unit` = ETH float. parsePriceToWei's
     `Number.isInteger(value) -> BigInt(value)` is therefore wrong for the GQL
     surface (T2.4). The GQL path must always treat `unit` as ETH.
  3. `is_eligible` is required on the REST surface, so a REST verdict is never
     null. The GQL `stages[].isEligible` IS nullable, which is why the local
     tri-state handling exists.
  4. The running-cap semantics are as quoted under T1.5.

Corrections to earlier items after re-checking against the docs:
  - T3.3 (uuid dash normalization) is LATENT, not live. Measured: the GQL
    inventory (CollectionDrops) and the GQL eligibility query return byte-identical
    uuids for all four jpegz stages, in OpenSea's own mixed formats
    (b88e9d0564cd46c3bb8b59c408dfcc7b undashed,
     f3de2b08-f40c-45ed-9a0a-80b27c02558e dashed). Both surfaces agree, so the
    raw-string join works today. Normalizing anyway is cheap insurance.
  - T2.4 is confirmed and narrowed: only the GQL surface is affected.
